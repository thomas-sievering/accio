# Thread delivery

One compact row above the composer: change counts, **Ship ▾**, and **Open app** when the project has a preview command.

Decisions are in [ADR 0015](../adr/0015-threads-own-delivery-with-optional-pull-requests.md). Browser coverage: `tests/delivery.spec.ts` and `tests/delivery-merge.spec.ts`; server coverage: `apps/worker/src/threads/deliveryObservation.test.ts`.

- **Ship** finishes the task, integrates the latest default branch, verifies it and publishes. Clicking during work queues a durable request; **×** cancels that request without stopping the work. A queued request survives disconnects and restarts. When accio restarts mid-Ship, the request stays and continues by itself: a delivery turn resumes on its session and checks what already happened before repeating anything, and a scripted ship runs again from the start. Only an explicit Stop pauses delivery until you resume or Ship again.
- With a **test command** in project settings, a direct Ship is a [scripted ship](scripted-ship.md): accio commits, rebases, runs the command and pushes without a model turn, and hands over to the agent only when something fails.
- **Prepare for review** runs the same preparation and opens a PR, without permission to merge. The workspace stays available for review fixes.
- The sidebar and composer show **Waiting for checks**, **Waiting for review**, or **Waiting for merge · #123**. A confirmed merge appears as **Merged · checking main** until target verification passes, then **Merged into main · #123**. Direct publication reads **Shipped to main**. Ordinary idle turns read **Ready**.
- Project settings choose direct publication or a PR for Ship. This applies to new requests; an existing request keeps its recorded policy and target.
- The server verifies the Git revision and GitHub check results independently of the assistant's prose. GitHub verification needs an authenticated `gh` CLI on the execution machine. Active waits are checked about every 30 seconds; prepared PRs awaiting merge about every two minutes, with backoff on observation failures. Only actionable failures or an authorized merge wake the owning agent, up to three continuations within an hour. Passive PR observation continues after that budget, after review preparation and across server restarts. Missing proof retains the workspace and records the blocker.
- If active workflows report no checks, allow two minutes for registration after the delivery request, or after a confirmed publication for target checks, then block with an explanation that workflows may exclude its paths or branch. Missing checks never count as passed.
- Newly verified deliveries automatically settle and write a durable completion notice. Settlement retains previews, files and the worktree. New work, an active turn, snoozing or an explicit Reopen prevents an older result from hiding the thread. Historical completed records are not bulk-settled. Stopping automatic follow-ups preserves a published PR and its observation, while keeping the thread open; a fresh Ship request is needed to authorize more publication.
- A newly auto-settled conversation stays selected, its Settled shelf opens once, and its merge/shipping badge remains visible. **Reopen** preserves an explicit keep-open choice; sending another message reopens the thread for new work. Observation errors show the last known state and retry without starting the model.
- **Archive** becomes available after delivery. It verifies again, stops the owned preview and removes only this thread's clean worktree and matching branch, preserving history. Snooze only organizes the list. Settling by hand also releases a worktree that holds no work (still at its start revision, no uncommitted or untracked files, no delivery, no running preview), so question and one-off threads don't pile up worktrees. Ignored files such as `node_modules` don't count as work. Anything else keeps its worktree. New messages in an archived thread provision a fresh worktree from its delivered revision. A thread released on Settle gets one from the latest default branch and keeps its harness session.

New threads in Git repositories with a commit get owned worktrees. With an origin remote, creation discovers and fetches its current default branch and starts at that revision. A failed fetch prevents creation and reports the problem instead of using a cached base. Without origin, new worktrees start from committed local HEAD. The source checkout's branch, local commits and uncommitted changes stay there. Archived threads restore their recorded delivered revision.

Existing threads, ordinary folders and empty repositories retain their original working directories and have no Ship/Archive controls. Original project folders are never deleted.

Preview commands run in the owned worktree with a separate `PORT`, `ACCIO_HOME`, `ACCIO_PORT` and `ACCIO_HUB_PORT`. `{port}` in the command is substituted; for example `pnpm dev --host 127.0.0.1 --port {port}`. The button opens only after an HTTP service responds. The wrapper stops its child process tree on normal shutdown or IPC disconnection. Only previews started by Accio are managed; unrelated shell commands or externally started services are not registered previews. This first implementation supports local web previews. Protected remote forwarding through the hub remains a later capability; the current product already gates remote thread execution.

## Later: generated replies

The pill to the right of **Open app** in the approved mockup is a **suggested user reply**, not another delivery action. Leave it out of this implementation.

Generate short, context-aware proposed answers with a cheap, fast model such as **Luna or Haiku**, separately from the thread's coding model. Selecting a suggestion should populate the composer for the user to edit and send. Suggestions carry no permission to publish, merge or clean up. Model routing, cancellation/staleness after new messages, cost limits and privacy/profile boundaries need to be specified before implementation.

## Open work

- **Link PR.** PRs created outside Ship / Prepare for review need an explicit Link PR action and a thread-scoped `link_pull_request` tool. A pasted historical link must not imply merge authority or trigger settlement.
- **Multiple PRs / stacks.** Delivery tracks the one PR associated with its request; stacks need every relevant outcome before settlement.
- **Infrastructure.** Protected remote preview forwarding through the hub, webhook wakeups instead of machine-side `gh` polling, project-wide publication coordination (ADR 0015), and registering processes started outside the preview runner. Current process tracking is not process isolation.
- **After publication.** Shipping updates origin's target branch only. Advancing the original checkout, restarting the user's app or checking a deployed version are not done.
- **Unverified.** Live GitHub authentication, real human review and live coding-provider turns; the browser fixtures substitute the harness and hosting reads.
- T3 Code's [settlement service](https://github.com/pingdotgg/t3code/blob/a10490937dbd8a9e441b0518a77a60117f3ecf5a/apps/server/src/orchestration-v2/ThreadSettlementService.ts) and [PR sync reactor](https://github.com/pingdotgg/t3code/blob/a10490937dbd8a9e441b0518a77a60117f3ecf5a/apps/server/src/orchestration-v2/PullRequestSyncReactor.ts) are useful references for the above. Unlike T3, Accio does not auto-settle closed PRs or inactive threads, and Archive remains its explicit cleanup.
