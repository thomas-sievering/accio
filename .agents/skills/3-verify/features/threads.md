# Coding threads, models and thread organization

Users choose a project or profile, select a model, send prompts, observe streamed replies/tools, interrupt or resume work, and organize conversations through search, filters and shelves.

## Sub-features

- `threads-picker`: project, multiple-checkout, hub project without a checkout here, another online machine's folder without a remote, and No project/profile entries with mouse/keyboard search.
- `threads-models`: provider tabs, provider groups, favourites, cross-harness handoff and borrowing another profile's accounts.
- `threads-turn`: first send, streaming transcript, follow-up, tool effects and persistence.
- `threads-drive-browser`: Run `pnpm exec playwright test --project=relay browser-pairing.spec.ts` after `pnpm build`. At the paired hub URL, open the MacBook's thread and change its model and Effort. Keep a draft through a thread switch and reload, then Send with Move on enabled and verify another inbox thread opens. Reopen the running thread; Send steers it and Queue stays in place. Edit and save a queued message, remove it, and Stop the turn. The separate request-card journey verifies that a choice screenshot renders and a picked option is sent, and that answering an `add_project` confirmation clears `Needs your OK` and lets the turn continue.
- `threads-stop`: stop from composer/row/menu; resume interruptions; retry failed turns.
- `threads-find`: title search, clear, profile/project filters and clear filter chip.
- `threads-organize`: rename, snooze/wake, settle/reopen, shelf expansion/paging, confirmed deletion.
- `threads-issues`: Pick an issue beside the machine in a project draft; GitHub and local `.scratch` trackers, search, keyboard pick, removable chip, the first message, the title, the claim, and issues in progress opening their thread.
- `threads-issue-offer`: a thread that published issues calls offer_issues; region `Issues to implement` lists them with Ready, Waits on, Claimed or Closed, Implement starts a claimed thread on a ready one, and the row then reads Started with Open thread.
- `threads-goal`: `/goal <objective>` in the composer shows the Goal bar (`getByRole('region', { name: 'Goal' })`); accio continues turns ("Continuing toward the goal" dividers) until finish_goal reports achieved or blocked; Pause, Resume and Clear goal buttons and `/goal pause|resume|clear`. Covered by `tests/goal.spec.ts` in `pnpm test:chat` with the scripted harness calling the real MCP tool; real-provider goals need a signed-in account.
- `threads-coordinate`: a thread that started threads with start_thread gets the deliver_thread and settle_thread accio tools (listed only once it has started one). deliver_thread requests Ship or Prepare for review through `threads.deliver`, as the composer's Ship does: it queues behind the started thread's running turn, refuses with Ship's reason where Ship is unavailable (queued messages, no origin, already requested, delivered, under way, already on the target) and the delivered thread settles by itself. settle_thread settles as the sidebar's Settle does. Both refuse a thread the caller did not start and one on an offline machine, and reach another machine's thread through the relay. Covered by `apps/worker/src/threads/startedThreads.test.ts` and the coordinator test in `delivery.test.ts` (start, queued Ship, delivered and settled against a real Git origin); the wake on `thread_state: "delivered"` when a delivery stops on a person (review, manual merge, closed PR) by `waits.test.ts`. There is no browser surface beyond the started thread's own delivery row and sidebar place.
- `threads-wait`: a harness calls the wait_for accio tool and ends its turn; the Wait bar (`getByRole('region', { name: 'Wait' })`) lists the conditions with Cancel wait, the sidebar places the idle thread on Working as `Waiting`, and once a condition is met accio starts the next turn with a `Wait met` message. Covered by `tests/wait.spec.ts` in `pnpm test:chat` ("Wait fixture: long|short" waits on a command); started-thread, pull request and timer conditions by `apps/worker/src/threads/waits.test.ts`. Real waits on another machine's thread need the relay fixture or two linked machines.
- `threads-needs-you`: a running harness calls the needs_you accio tool with an action; the row leaves `Working` for the inbox reading `Needs you` while the spinner-free turn keeps running, region `Needs you: <action>` shows the card with Done, and Done (or any message, the agent's `done: true`, or the turn ending) collapses it to `Done`/`Ended with its turn` and returns the row to `Working`. A pending Confirmation reads `Needs your OK` the same way.
- `threads-reactions`: select text in an assistant message, pick 👍/❓/👎 from toolbar `React to the selected text`; a chip `.composer-reaction` joins the composer (its emoji switches the reaction, `Remove … reaction` drops it), survives reload, and sends as a fenced `reaction: …` block shown as `.reaction-card` in the message. Covered by `tests/reactions.spec.ts` in `pnpm test:chat`; the scripted harness echoes the reactions it read.
- `threads-move-on`: a send that starts a turn opens the top of the inbox other than the sent thread, its draft kept with the cursor at the end, or region `Empty page` when the inbox is empty. Clicking Ship (nothing written, so it ships rather than arms) moves on the same way once the server accepts the delivery. A reload stays on the empty page. Steering (Enter) and queueing (Ctrl+Enter) stay put, and so does a new thread's first message. Settings / Sending has switch `Move on after sending`, on by default and kept per client (`localStorage` `accio.moveOn`). Covered by `tests/move-on.spec.ts` in `pnpm test:chat`, including Alt+Enter (Ship when done) still shipping the thread it moved on from, and the Ship button; the other Playwright specs start with it off (`playwright.config.ts` storageState), so clear that when a journey needs the default. Picking the next thread: `nextAfterSend` in `apps/web/src/threads/shelves.test.ts`.
- `threads-delivery`: owned Git worktrees, Ship/review intent, cancellation, remote verification, preview ownership and safe Archive.
- `threads-ship-when-done`: while the composer holds a message, Ship (`aria-pressed`) or Alt+S arms the `.composer-ship` chip (`Ship when done`, or `Review when done` after choosing Prepare for review); `Remove Ship when done` or Alt+S removes it. With the composer empty, Alt+S anywhere in the open thread presses Ship (ships and moves on); in another text field such as the sidebar search it does nothing. Sending with it, or Alt+Enter without it, sends and then queues the delivery behind the turn (`Ships when done` in `.delivery-actions`). Covered by `tests/ship-when-done.spec.ts` in `pnpm test:chat`.

## How to get to it (user POV)

- Sidebar `New thread` button; the idle pane also has `New thread` after setup is complete.
- Pick a project, then a checkout if multiple exist; alternatively pick `No project`, then a profile if multiple are available.
- Select an existing thread row to reopen its transcript. Its right-click menu exposes thread actions; hover buttons also expose Stop/Snooze/Settle/Wake/Reopen where applicable.
- Desktop app only: right-clicking elsewhere opens a native menu (`apps/desktop/src/contextMenu.ts`) with spelling suggestions and Add to dictionary, Cut/Copy/Paste/Select All in the composer, Copy for selected text, Copy Link and Copy Image. Browser tests cannot reach it; its unit test covers the items.
- Sidebar `Search threads`, `Filter threads`, and nonempty `Working`/`Offline`/`Snoozed`/`Settled` shelves organize the list. A running thread, or one whose delivery waits on CI or merges itself, sits on `Working`; it returns to the top of the main list about two seconds after it finishes, at once when it fails or needs a secret, review or manual merge. Another machine's thread moves to `Offline` (folded by default; its header counts its threads, `Offline 2`) once that machine has been offline for ten seconds, and back to the top of the main list ten seconds after the machine returns; settled and snoozed threads stay put.

## Driving it with Playwright

Preconditions: healthy instance. New thread, search and filter stay hidden until some profile has a signed-in account and a project exists, so the offline baseline reaches none of these journeys. The signed-out gate needs a second, signed-out profile beside a signed-in one. A successful turn requires a real signed-in selected provider account and a reported model; a project thread also needs the disposable folder added. Search/shelves need actual threads; paging needs more than five settled threads. The baseline supplies none of these authenticated thread fixtures; for a signed-in account use the verify device (`pnpm verify:real`, see [Real model turns](../SKILL.md#real-model-turns)). Report unavailable journeys as failed prerequisites/unverified coverage; never insert fake threads into storage to call this an end-to-end proof.

Click exact `Send` (also exercise Enter and Shift+Enter on separate follow-ups). Require the user prompt in `.messages .msg.user`, a real assistant reply containing `ACCIO_VERIFY_OK` in `.messages .msg.assistant`, and a completed nonfailed thread in the sidebar. Reopen and reload; require preserved user and assistant items. The model's exact prose beyond the requested marker may vary.
- **Tool side effect.** In the disposable project only, request creation of `accio-verify.txt` containing `ACCIO_VERIFY_FILE`. Require the rendered tool activity and actual file/content under `fixture`. Capture prompt, tool/result transcript, file contents and `git status` if using a git fixture. ## Gotchas

- **Search across shelves.** Create a uniquely titled thread through Send, settle
  it through Thread actions, then search its exact title. Expand Settled and
  require the matching row; check that `No threads found.` does not appear
  alongside it. Repeat with a snoozed thread. The November 2026 audit found the
  empty-state message counts only drafts, open and Working rows, so a passing
  ordinary search does not cover these branches.
- **Row motion.** Each sidebar row sits in a `.row-slot` (`threads/SlidingRows.tsx`).
  Status changes (snooze, settle, reopen, delete, a turn starting or ending) slide the
  remaining rows for about 320ms and fade removed rows, so an `.row-slot` can stay in
  the DOM at falling opacity after its thread is gone; wait for `toHaveCount(0)`
  rather than asserting removal at once. A row crossing between lists carries
  `data-travelling` while it moves. Search, scope and profile filtering are instant,
  and an emptied shelf fades out with its last row. `tests/sidebar-motion.spec.ts`
  covers these, the picker's first-open-only stagger, and the shared press sink.
- **Completion motion.** Record a paced first turn through its completion and
  the two-second Working delay using [smooth-ui](../../smooth-ui/SKILL.md).
  Inspect the selected row's move from Working into the open list, the last
  Working shelf disappearing, and adjacent rows moving. DOM coordinates alone
  cannot establish motion because view transitions render separate snapshots.
  After the real thread has opened, focus its Working row and wait for the move;
  require focus to follow that thread rather than fall back to the document body.

- **Mentions:** `tests/mentions.spec.ts` in `pnpm test:chat`. A bare `@` lists Models, Machines and Threads (listbox `Mention a model, machine or thread`); Enter or a click opens one, Backspace on the bare @ goes back. Typing after @ lists matches of every kind. Threads group as Open, Working, Offline, Snoozed and Settled, as in the sidebar. In the composer each resolved mention is a pill in `.composer-backdrop` over the transparent textarea; the sent message shows a `.mention` chip, a thread's with its title. What the agent reads (a line per mentioned thread after the message) and read_thread on another thread are covered by `apps/worker/src/threads/threadMentions.test.ts`. A `/` at the start or after a space lists the skills the thread (or draft) gets next turn (listbox `Use a skill`), filtered by name then description; picking one inserts `/name ` (last test in `tests/mentions.spec.ts`).
- **Recall last message:** `tests/recall-message.spec.ts` in `pnpm test:chat`. Up in an empty composer (no text, Pasted text, Reactions or images) fills it with the typed text of your last message in the thread, cursor at the end; turns accio started (Goal, Wait met, Resumed) are skipped. With a draft, Shift/Ctrl/Alt/Meta, during IME composition, while the `@`/`/` menu is open, or in a thread with no sent message, Up does nothing special. The restored text is an ordinary draft: it survives reload and sends edited. Picking the text is covered by `apps/web/src/threads/lastMessage.test.ts`.
- **Issue picker:** `tests/issue-picker.spec.ts` in `pnpm test:chat`. The fixture's `issues-project` has a GitHub origin and a faked gh; `scratch-project` has local issue files. Require groups Ready for agent, Needs triage and Blocked (GitHub) or one per feature (local), the list opening below the chip, a searched Enter pick, the composer chip and `#208 · claims on send`, a first message `Work on #208: …`, a thread titled from the issue, and the recorded `gh issue edit 208 --add-assignee @me`; a later draft then lists #208 under In progress, where Enter opens its thread and its New thread button attaches it again; locally, `Status: claimed` in the thread's worktree only. A project without issues shows no chip. Real GitHub assignment needs a disposable repository; never claim on the user's tracker.
- **Issue offer:** the last test in `tests/issue-picker.spec.ts`. In `issues-project`, sending `Publish the tickets` makes the scripted harness offer #205 and #194. Check that region `Issues to implement` shows #205 as Ready with `Implement #205 in a new thread`, and #194 as `Waits on #205` with no button. Clicking Implement must turn the row to Started and record `gh issue edit 205 --add-assignee @me`. Open thread must then show `Work on #205: …` followed by the implement skill line. Checking refs against the tracker, refusing a ref it doesn't list, a blocked issue or a second start, and the mention of the planning thread are covered by `apps/worker/src/threads/issueOffer.test.ts`.

- **Prompt size:** see [System prompt](system-prompt.md) for the composer stat, persistence check and measurement scope.

- **Context window and prompt cache:** run the `Claude cache usage` case in `tests/inline-chat.spec.ts` against the chat fixture server. Send `Cache usage fixture` from a new No project thread; require the `.context-meter` pill to read `1k / 200k` (the fixture's reported 200,000-token window), open it, require the meter with its compaction tick and `Compacts automatically at about 167,000 tokens.`, the limits row and `Prompt cache 80% read`, open that breakdown, and require 800 read, 100 written, 100 reported one-hour writes and 100 uncached tokens. Reload and reopen the breakdown with the same counts. The fixture substitutes the coding harness at the production boundary; this proves persistence and UI accounting, while live Anthropic cache hits remain unverified. Main-conversation request usage excludes subagents, title generation and older requests without usage reports.

- **Markdown tables:** the `wide Markdown table` case in `tests/inline-chat.spec.ts` sends `Table fixture` and requires, at 1280 and 390 px, the wide table's `.table-scroll` to scroll while `.messages` never scrolls sideways, and the narrow table to keep its own width. Headless Chromium hides scrollbars; check the visible horizontal scrollbar with `--headed`.

- Sending creates the thread; opening a draft alone does not persist a conversation.
- Coding harnesses have full permissions. Keep all tool tasks inside the runner's disposable project; never test a prompt against the user's checkout.
- Favourites may initially be empty while provider tabs contain models. Empty favourites is not an empty provider catalog.
- Search matches thread titles, not transcript contents. Rename a real thread before testing a specific search term.
- Shelves exist only when nonempty and default to collapsed. Profile/project filters and search affect their contents too.
- The baseline has no provider authentication, real turn, multi-checkout fixture or six-thread paging fixture. Keep each missing branch explicit in coverage.
