# Tools, MCP servers and skills

The hub owns definitions and selections. Tools execute on this machine; remote HTTP MCP credentials stay on the hub; skill sources are Git snapshots. Tools and MCP servers are available to all profiles and projects. Skill selections are additive across global, profile, space and project scopes; no selection means optional. A space's skills are its home's skill files plus library skills turned on for the space (`spaceIds` in the selection); a thread in the home gets those files as Project skills instead. When levels share a skill name the narrowest wins (Project over Space over Profile over Everywhere, ADR 0020) and the wider one is overridden; a clash within one level is a conflict. Skills installed on the machine (`~/.agents/skills`) never reach a thread: Codex turns pass them as disabled.

## Run the repeatable settings journey

Run `node .agents/skills/3-verify/scripts/verify.mjs .agents/skills/3-verify/scripts/resources.mjs` after building. It uses the production server and disposable home from the verification runner. It creates its profile, project and Git skill source through UI actions, then retains actions, screenshots, ARIA snapshots and read-only persisted observations. The failing-install check reaches npm and requires network access. A failure to reach npm is not evidence of a package-not-found response.

This journey covers the settings flows below with a signed-out profile. It does not prove successful provider sign-in, repair execution, a real MCP service's OAuth flow, or multiple-machine behavior. Report these separately with their prerequisites.

## Entry points and expected outcomes

- `tools-settings`: Settings sidebar -> Tools -> Add tool. Use preset fills the Playwright CLI package, executable and exact version. Invalid versions show an inline error. Save with no scope controls; installation starts immediately. Require Ready after a successful check and reopen to confirm saved values.
- `tools-readiness`: Settings → Tools → named tool, and Settings → Machines → this machine → Managed tools. Compare version, check time and failure details. Install and check runs locally. Failed checks show Needs attention and either Open repair thread or the reason one could not start. Remote actions are unavailable in v0.1.
- `tools-repair`: Requires a signed-in profile with an available model. Make a disposable tool's check fail, require one local repair thread, and open it from its status card. Repeated checks must reuse that thread. Let the repair finish; require a new health-check result before accepting Ready. Inspect the transcript and managed installation as second observations. A signed-out refusal covers only the blocked branch.
- `mcp-settings`: Settings → MCP servers → Add MCP server. Choose Remote (HTTP), enter URL and authentication, save without scope controls. Local command (stdio) instead takes a command and one argument per line. Reopen each definition and confirm transport and values.
- `mcp-token`: On a saved bearer server enter Bearer token and Save token. Require the saved-state message and an empty/hidden input; the saved token must not appear in page HTML or `hub/resources.json`. Sign out clears the saved credential. Use a disposable test token, and preserve only assertions about the secret store, never its contents.
- `mcp-oauth`: Requires a reachable service with supported OAuth metadata and a callback reachable from the browser. Choose OAuth, save, then Sign in. Complete consent and require Signed in. Repeat with Complete sign-in using the full callback address. Sign out and require Signed out. Failure stays visible; an unreachable test service proves only the failure branch. Test cancel and expiration separately.
- `skills-source`: Settings → Skills → Add skill source. Enter Name, Git URL and optional ref; Add source. The resulting source shows repository, followed ref, active commit and imported optional skills. A source with no SKILL.md must show its error.
- `skills-update`: Commit a change in the disposable source, then Check for updates. Require the new revision preview while the persisted active revision remains unchanged. Apply the revision, reopen and require the new active revision with existing selections retained. Select a previous revision to prove rollback. Preview compares names and descriptions; its hint states that other files may also have changed.
- `skills-scope`: In a source's skill row click `Enable for…`, select profiles, spaces (listed once a space exists) or projects, or Enable everywhere, then Save. The row's summary names them. Reopen and compare the skill scope in `hub/resources.json`.
- `skills-copy`: In the skill row choose Copy into project, select Checkout on this machine, then Copy. Require the returned path and read the resulting `.agents/skills/<name>/SKILL.md`. A second copy must refuse to overwrite it. The copy belongs to project Git; its source no longer updates those files. When a project copy and a synced skill turned on for the same project share a name, turn preparation reports the conflict until one is disabled; a synced skill of that name turned on for the profile or Everywhere is overridden instead.
- `skills-panel`: Open a project thread, toggle Side panel, Skills tab. Each skill level (Project, Space, Profile, Everywhere) is its own fold, all folded at first with available/loaded counts; Profile and Everywhere are left out when empty, and an opened fold stays open across threads until the app reloads. Project lists repository files (Repository) and project-enabled library skills. Add skill searches disabled library skills and enables one for the project; Disable for this project removes it. Expanded rows show instructions, source and path; Reference in message inserts into the composer; repository instructions save to the checkout's file. Loaded appears only for an observed instruction read or explicit invocation and jumps to that transcript item. Switching to a thread without a project shows No project. Space appears only when the thread's project is in a space (it reloads when spaces change): it lists the home's skill files (tag Home, source "The space’s home", read-only) and library skills turned on for the space (Space · <source>); its + ("Add skill to the space") turns one on for the space and Disable for this space turns it off. After Everywhere comes a read-only, folded section titled with the thread's (or the draft's chosen) harness, Claude or Codex, tooltip "Ships with …", listing its harness skills with no origin label and no switch; Claude doesn't share their instructions, Codex's open from its home. Last, Overridden lists skills turned on at a wider level whose name a narrower level also has: dimmed, tagged "Overridden by Project" (or Space, Profile) instead of Loaded, with their level in the tag's tooltip. Covered by `tests/skills-panel.spec.ts` in `pnpm test:chat` with the fake harness reading a repository SKILL.md, a library `repo-notes` turned on Everywhere and two fake Claude harness skills, and the Space level with `skills-home` as the home of a space the test arranges through the API, including Settings → Skills → Library → lib-review → Enable for… → Spaces; real-provider loads and real Codex harness skills remain unverified there (the worker suite covers Codex's `skills/list` through a fake app-server).
- `resources-project`: Open project settings -> Skills. Only skills have selection controls; tools and MCP servers have none. Inherited global/profile skills are checked and locked, with their origin explained.
- `resources-profile`: Settings -> Profiles -> named profile -> Skills. Only skills have selection controls. Toggle an optional skill and reopen; require its profile selection without losing project selections. Global skills remain inherited.
- `resources-delete`: Tool and MCP detail require a second delete click. Skill sources require Delete source followed by the named confirmation. Confirm disappearance after reopening. Deleting a definition does not delete project-owned skill copies.

## Proof boundaries

The hub stores non-secret definitions and selections in `hub/resources.json`. A turn's transcript records the resolved tool versions, skill revisions and MCP names. Successful settings saves alone do not prove resource use by a harness. The backend suite exercises repair execution with a fake model, OAuth with a fake service and the real bundled Codex discovering an HTTP MCP through the hub. Real provider consent and paid repair turns remain separate live checks.
