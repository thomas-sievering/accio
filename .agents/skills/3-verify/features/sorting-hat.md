# Sorting Hat

A hub can run its threads through a Sorting Hat of its own (ADR 0018): Settings / Hubs takes its address and an admin token pasted from its dashboard, each profile links to one of its houses, and a thread gets a hat key for its profile's house and its machine, plus the Sorting Hat's address. Without one, the hub keeps accounts itself, as before. The admin token stays on the hub: no client, protocol message or thread receives it.

Run `node .agents/skills/3-verify/scripts/verify.mjs .agents/skills/3-verify/scripts/sorting-hat.mjs` after building. The journey starts a standalone Sorting Hat from `apps/sorting-hat/dist/main.js` in the run's scratch folder and stands in for its dashboard through the admin API: houses `Personal` (with a signed-out `Dashboard Claude`) and `Work`. Nothing contacts a provider and no turn is sent.

Mapped entry points:

- `sorting-hat/settings`: Settings / Hubs → card `Sorting Hat` → textboxes `Address`, `Admin token` (a password field; use `getByLabel`), `This hub’s name on the Sorting Hat` (prefilled with the saved hub's name) → `Connect Sorting Hat`. A wrong token must show "The Sorting Hat refused the admin token…" in the card's alert. Connected, the card shows the host, `<n> houses` and "Hat keys are named “Accio · <name> · …”." with `Change` and `Disconnect`; `Disconnect` asks first ("Threads go back to the accounts this hub keeps itself…"), then deletes the hub's hat keys on the Sorting Hat. The page and `<home>/hub/*` must not contain the admin token after saving.
- `sorting-hat/profiles`: a profile without a house reads `<name> No house on the Sorting Hat` in Settings / Profiles. Its form has the MenuSelect `House on the Sorting Hat`; picking another house hides the account lists until Save ("Save to use the accounts of <house>."). Saved, the row reads `<name> House <house> · <accounts>` and the account lists show the house's accounts; changing them sets the house's accounts on the Sorting Hat, for every app using it. `profiles` in `<home>/hub/settings.json` carries `houseId`.
- `sorting-hat/threads`: a draft or thread of a profile without a house shows "<name> isn’t linked to a house on the Sorting Hat, so this thread can’t run yet." with `Choose house`, which opens that profile; Send stays disabled. Starting a turn anyway (RPC) answers the same message.
- `sorting-hat/accounts`: Settings / Accounts lists the Sorting Hat's accounts with a note to change them on its dashboard, and offers no `Add … account` row. Account writes answer that the accounts are on the Sorting Hat (until account settings work through it, #136).

The journey covers all four, with signed-out accounts only. A real turn through a Sorting Hat (a linked hub configured with one, signed-in accounts in its houses) is not part of it; `apps/worker/src/threads/sortingHat.integration.test.ts` runs Claude Code and Codex turns through a standalone Sorting Hat with faked providers, and `apps/hub/src/sortingHatLink.test.ts` covers hat-key naming, reuse across restarts, unpairing and disconnecting. Report live-provider turns through a deployed Sorting Hat as unverified unless driven.
